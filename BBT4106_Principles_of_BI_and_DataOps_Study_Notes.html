01 Definition of Technical Jargon

Decision-making benefits from using past data to predict the future, then acting on those predictions — e.g. forecasting item demand from past sales to avoid overstocking or understocking. A business usually holds data across many departments (Porter's Value Chain: primary functions like inbound logistics, operations, outbound logistics, marketing & sales, service; support functions like HR, technology management, procurement, firm infrastructure).

Data Marts, Data Warehouses & Data Lakes

For performance and organisational control, businesses extract data from multiple sources and load it into a shared store.

Data mart — a subset of a data warehouse, oriented to one department/function.
Data warehouse — stores data for the whole business, using a unified schema (easier querying, some redundancy).
Data lake — gathers data with little pre-processing; keeps structured, semi-structured & unstructured data. Needs flexible querying tools (NoSQL — "Not Only SQL"), e.g. Spark SQL, SPARQL, Cypher, Gremlin, MongoDB Query.

Data Mining vs Data Analytics vs Business Analyst

Data mining discovers new patterns/rules from large volumes of data — it uses techniques from probability, statistics, linear algebra, AI, and programming, and does not start from a prior hypothesis.

Data analytics starts from a hypothesis or question ("why did sales drop last quarter?") and focuses on answering it to drive action, using tools like SQL, Power BI, Excel.

Gold Mine AnalogyData mining is the excavation — digging through raw data to find a vein of gold (a hidden pattern) without knowing exactly where it is. Data analytics is the jewellery store — taking that raw gold and refining it into something usable (a report or strategy).
FeatureData MiningData Analytics
Primary goalFinding hidden patterns/correlationsAnswering specific questions
Starting pointLarge, often unstructured datasetsA specific hypothesis or business need
Human elementMostly automated/algorithmicHighly interpretive, strategy-focused

A business analyst focuses on improving business processes, operations and strategy — acting as a liaison between stakeholders, doing stakeholder interviews, gap analysis, requirement specification, and process improvement. Data mining finds patterns → data analytics turns them into insight → business analysis turns insight into an organisational solution.

Quick tip: Enjoy math/coding → data mining/data science. Enjoy storytelling with data → data analytics. Enjoy problem-solving with people → business analysis.

Deductive & Inductive Reasoning

Knowledge progresses from raw data → information → knowledge (the DIKAR model: Data–Information–Knowledge–Action–Results).

Deductive reasoning — applies prespecified general rules to discover new specific information.
Inductive reasoning — applies observed specific data to discover new general rules. Data mining applies inductive reasoning.

Discovered knowledge can be represented as rules, propositional logic, or structured forms (decision trees, neural networks, regression models). Types of knowledge discovered: association rules (e.g. cart items "a" and "b" imply "c"), classification hierarchies, clusters, time-series patterns, and sequential patterns.

Knowledge Discovery in Databases (KDD)

KDD is a methodology for applying inductive reasoning to discover generalisable knowledge, in 9 iterative steps:

The 9 Steps of KDD
1. Problem Definition→ 2. Data Selection→ 3. Cleansing & Pre-Processing→ 4. Data Transformation→ 5. Select Mining Task→ 6. Select Mining Algorithm→ 7. Utilisation→ 8. Interpretation & Evaluation→ 9. Consolidation
  1. Problem Definition & Goal Setting — understand the problem, end-user requirements, and environment.
  2. Data Selection — discover and integrate accessible data ethically (informed consent) and without bias (representative sample); done by the data engineer.
  3. Data Cleansing & Pre-Processing — remove outliers/noise, impute missing data (e.g. fixing invalid postal codes, currency symbols).
  4. Data Transformation — scaling, centering, standardisation, normalisation, Box-Cox/Yeo-Johnson transforms; encoding (one-hot, label/ordinal); dimensionality reduction. Done by the data analyst.
  5. Selection of the Data Mining Task — describe (associations/clusters), predict (class/value), or optimise (prescribe action).
  6. Selection of the Data Mining Algorithm — "bench test" several algorithms, shortlist top performers.
  7. Utilisation of the Algorithm — train the model; hyperparameter tuning and ensembling.
  8. Interpretation & Evaluation — validated by domain experts (not the IT practitioner) — e.g. via Hugging Face Spaces, Render, Streamlit. If invalid, repeat from Step 2.
  9. Consolidation — operationalise the knowledge into an information system; the hardest step, since production data is dynamic (not the clean "lab" data used to design the model).
Note: Data mining must be preceded by significant data preparation (Steps 1–4) before it yields useful, decision-influencing information. Modern non-linear/iterative alternatives to KDD include CRISP-DM, Scrum, Data-Driven Scrum, Kanban, SEMMA, and TDSP.

Business Intelligence, Data Science & Machine Learning

Business Intelligence (BI) — the process of creating a culture that makes evidence-based, rational decisions from insights that are accurate, reliable, timely, and actionable (Olszak, 2016). Gartner reframed BI as "Information-as-a-Service" — a culture where every employee can make evidence-based decisions.
Data Science — an interdisciplinary field (statistics, visualisation, social science, NLP, data mining) used primarily for scientific purposes. Data mining is a subset of data science.
Machine Learning (ML) — teaches a system to learn/adapt from data using algorithms, without explicit human instructions (unlike data mining, which relies on and is designed for human consumption).
Tom Mitchell's Learning Problem Triplet (1997): "A machine learns with respect to task T, performance P, and experience E, if it reliably improves P at T following E."

Example — Task: classify spam emails. Performance: % correctly classified. Experience: watching users mark emails "Spam".

This describes Narrow AI: being excellent at one task (P at T) does not imply general intelligence. "Machine Learning" is an anthropomorphism — the machine performs statistical convergence, not conscious reasoning.

Relationship between fields: AI enables decisions without human intervention → Machine Learning (Supervised, Unsupervised, Semi-Supervised/Reinforcement) provides statistical tools to analyse data → Deep Learning mimics the brain via neural networks (ANN for numeric data, CNN for images, RNN for time series, Transformers for NLP/sequential data — the backbone of LLMs) → Data Science wraps all of this plus the scientific method and domain knowledge.

02 Terminologies Used to Describe Data in BI

Data can be described from two perspectives:

Statistical Perspective

Frames data as a hypothetical function f the algorithm is trying to learn: Output = f(Input). Multiple input variables form an input vector. Input variables are independent variables (X); the output variable is the dependent variable (Y): Y = f(X). Example: Exam Score = f(Hours of Study).

Computer Science Perspective

A row of data = an instance (an observation about an entity). A column = a feature (or attribute). The output feature is the target — also the prediction.

Prediction=Program(Instance)

A model is the specific representation of knowledge learned from data; an algorithm provides the process of learning that representation: Model = Algorithm(Historical Data), then Prediction = Model(New Data).

Data mining/ML algorithms learn a target function f mapping X → Y (predictive modelling — the most common data mining task). There is also an irreducible error (e) independent of X — e.g. missing attributes needed to fully characterise the true mapping.

04 The Bias-Variance Trade-Off

Model error is either bias error, variance error, or irreducible error (cannot be reduced regardless of algorithm — caused by the problem's framing, e.g. unknown influencing variables).

Bias Error

The simplifying assumptions a model makes to learn the target function faster. Linear/parametric algorithms (e.g. linear/logistic regression, LDA) have high bias — fast to learn, easy to understand, but less generalisable.

Causes of bias:

  1. Biased training data — e.g. a hiring model trained only on graduates from specific private universities perpetuates representation bias.
  2. Limited or skewed data — e.g. a "VIP customer" model trained 90% on high-density urban stores misses high-value peri-urban spenders (sampling bias).
  3. Oversimplification bias — underfitting from a model too simple for the data's complexity.
  4. Poor feature selection — e.g. a decision tree using "place of residence" purely because it gives a clean mathematical split, even though it is unethical.

Variance Error

How much the model's estimate changes when you swap training batches. Non-linear algorithms have high variance — large changes in the learned model when the training set changes. High training accuracy is actually a red flag for high variance.

Causes of variance:

  1. Model complexity ("over-thinker" effect) — the model memorises training points instead of learning the trend.
  2. Small training datasets — under ~200,000 observations is generally too few for data mining/ML; random outliers get treated as universal laws.
  3. Curse of dimensionality — too many features relative to rows creates fake correlations (e.g. a credit model "learning" that Firefox users who like scrambled eggs never default).
Remember: Bias is an error of assumptions (thinking you already know the answer); variance is an error of sensitivity (being too influenced by what you just saw). Decreasing bias increases variance and vice versa — the goal is low bias and low variance.

05 Underfitting and Overfitting

Generalisation is how well concepts learned by a model apply to examples not seen during training.

AspectUnderfittingOptimal (sweet spot)Overfitting
Model typeToo simple (parametric/linear)Just rightToo complex (non-parametric/non-linear)
BiasHighLowVery low
VarianceLowLowHigh
GeneralisationPoorExcellentPoor

Overfitting — learning training data too well at the expense of generalising; more common in flexible non-parametric algorithms. Mitigated using resampling methods or a held-back validation dataset.

Underfitting — failing to learn the problem sufficiently; easy to detect with a good performance metric, then fix by trying an alternative algorithm.

The "sweet spot" is just before test-set error starts rising again as the model overfits. k-fold cross validation is the gold-standard resampling technique: train the model k times on different folds and summarise results. If accuracy varies wildly between folds (e.g. 90%, 50%, 88%) that's a high-variance model caught hiding behind a few lucky data points. 5-fold or 10-fold CV is standard practice.

Validation vs test set: The validation set is used during training to tune the model (find the sweet spot); the test set is the "final exam" used once at the end to confirm the model actually works.

06 Data Products

Data is the new oil — but raw oil is useless. A data product is the refinery.

A data product is a purposefully designed digital asset that packages data, logic, and interfaces to deliver reliable, timely, actionable insight for its intended users — it is purposeful (solves a defined problem), reliable (tested, maintained, trusted), and actionable.

Raw DataData Product
Collected passivelyDesigned intentionally
No defined userBuilt for specific users
No quality guaranteeTested and validated
Requires expertise to interpretDelivers ready-to-use insight
No ownershipHas an accountable owner

Examples

  • Analytical/Reporting: interactive sales dashboards, brand-sentiment tracking
  • Predictive: churn prediction, demand forecasting
  • Operational/Real-Time: fraud detection (e.g. M-Pesa), algorithmic trading
  • Experience/Personalisation: recommendation engines (Netflix), NLP chatbots (banking assistants)
  • Data Access: data APIs (weather data for logistics), geospatial analysis for site selection

Defining a Data Product — 6 Questions

  1. Problem Definition — what, where, since when, why unsolved, who's affected? Distinguish the symptom ("sales are declining") from the root problem ("sales team has no regional product-line visibility").
  2. Data Sources — which departments hold the relevant data?
  3. User Requirements — what does the user need (not just want)?
  4. Data Transformations Required — cleaning, aggregation, modelling needed.
  5. Intended Users — internal-facing (employee dashboard) vs external-facing (customer-facing score).
  6. Priority/Ranking — value relative to other data products competing for resources.

Success is measured by what a user cannot do today versus what they can do after the product ships — e.g. a loan officer moving from manually reviewing 500 applications/week to a risk-scoring model processing 10,000 consistently.

Data products are built using structured methodologies (CRISP-DM, Data-Driven Scrum/Kanban, KDD, TDSP, SEMMA) in incremental milestones, not one big release. Testing is essential — unit, integration, load, and API reliability testing, done continuously.

Lifecycle: A data product isn't complete until it's in production with a go-live date and a named owner. Without an accountable owner: data goes stale, models drift, dashboards show last quarter's figures as current, and fraud systems become liabilities.

07 Challenges Faced by Data Teams

  1. Friction with the business team — business expects delivery in days, data teams historically deliver in months.
  2. Demand outstrips capacity — multiple departments request data products simultaneously, creating backlog.
  3. Manual/waterfall processes reduce capacity — any change causes a domino effect through the lifecycle. Agile methodologies produce Minimum Viable Products (MVPs) with "small wins" instead.
  4. Unplanned work reduces output — informal ad-hoc requests hijack planned time.
  5. Ungoverned self-service — teams avoid the data team ("loading data takes too long", "I can't trust the data"), leading to silos and duplicated/divergent datasets.
Data Mesh (Dehghani, 2022) addresses silos via four pillars: Domain-Driven data ownership, Data as a product, Self-Service infrastructure platform, and Federated computational governance. Domain teams own and maintain their own data products rather than centralising everything in one data team.

Organisations aim to balance Governance and Agility — sometimes called "governed agility" or "agile governance".

08 DevOps (based on Continuous Delivery)

DevOps — introduced in 2009 by Patrick Debois — is a set of practices, tools, and cultural philosophy that automates and integrates software development (DEV) and IT operations (OPS) to deliver better software, faster. It traces back to Lean Manufacturing (Taylor, Fayol; pioneered at Toyota by Shingo and Ohno in the 1930s).

The DevOps loop
Plan→Develop→Test→Deploy (DEV)→Release→Operate→Monitor (OPS)↻

DEV cycles are measured in hours (at most days) — this requires MVPs. OPS matures from weekly/monthly deployments toward continuous deployment with regression monitoring.

VariantFocus
DevSecOpsSecurity built into the pipeline, not bolted on at the end
DataOpsDevOps principles applied to data pipelines and ML workflows
MLOpsManaging the ML model lifecycle in production
GitOpsInfrastructure/deployment config stored and driven from Git
FinOpsCloud cost management and financial accountability

DataOps is a collaborative data-management practice improving communication, integration, and automation of data flows between data managers and consumers, creating feedback loops for continuous delivery. Without a methodology, teams solve the wrong problem in the wrong order. Without continuous delivery, a good data product breaks silently in production and nobody notices until a bad decision is made (e.g. a bad loan approved).

09 The 7 Pillars of DataOps

1ELT and the Spirit of ELT — load data in raw form first, transform after (faster loading, no detail lost, supports governance/auditability/lineage). Exception: EtLT when regulation requires removing PII before mining (Kenya Data Protection Act 2019, GDPR, HIPAA, FERPA, PCI DSS, SOC 1/2/3, FedRAMP).
2CI/CD — frequently integrate changed code with the central repo, build, test, and keep it deployable on demand; DATA cycle measured in hours/days. Built on SCM (e.g. Git) plus tools like Jenkins.
3Component Design & Maintainability — small, atomic, reusable pieces of code, guided by Unix philosophy: clarity over cleverness, transparency, modularity, composition, orthogonality, simplicity, documentation, minimised interdependency, design for debugging.
4Environment Management — quickly spin up environments that mirror production (even duplicating terabytes of data), typically via Cloud Service Providers (GCP, AWS, Azure, OCI, Alibaba Cloud).
5Governance & Change Control — every change, test, and approval fully documented and retained to prove how data has been used.
6Automated Data Testing — catches errors before production; paired with ongoing monitoring of production data/artifact quality (not just system uptime).
7Collaboration & Self-Service — collaboration is a behaviour (psychological safety, shared accountability, aligned incentives), not a tool you deploy.

Together, the goal is to run the data team like a high-performing, predictable, quality-oriented manufacturing line — delivering high-quality data faster.

10 The DevOps and DataOps Toolchain

A toolchain is an ordered set of tools chained so each tool's output feeds the next — like stations on a manufacturing production line.

Watch out for toolchain sprawl: each new tool solves a real problem, but 14 disconnected tools later, onboarding takes weeks just to configure a laptop. Consolidation is usually more valuable than addition — master a few essential tools deeply (Git being foundational) before reaching for more.

11 Software Configuration Management (SCM)

SCM manages changes to source code, configuration files, and dependencies — aiming for consistency, traceability, and reproducibility.

The remote repository (origin) — hosted on GitHub/GitLab/Bitbucket — is the shared reference point. The local repository has a working directory (edit files), a hidden .git directory (history/metadata), and a staging area (index) — an intermediate space where changes are reviewed before committing, enabling precise, logical commits.

12 Branches for Team Governance

A branch is a governance decision, not just a Git feature. main should always stay stable and deployable; features, bug fixes, and hotfixes each get their own branch. If a feature fails, its branch is simply deleted with no damage to main. Code review happens on the branch before it touches main (via a Pull Request); conflicts during merge are a natural part of collaboration, not a failure.

Branch #1 → PR → Code Review → Merge→ Branch #2 (next task)→ Branch #3→ Branch #4 (sub-task)

Three ways to merge into main: Git Merge, Git Rebase, Squash Commits.

13 Git Merge, Git Rebase & Squash Commits

Git Merge

Creates a new "merge commit" combining both branches while preserving full history of each — "tying two branches with a knot; the knot and both branches remain." Maintains a complete snapshot of history, but can make it messy.

git checkout main
git merge feature/1          # creates a merge commit

git merge --ff-only feature/1   # fast-forward: no merge commit, pointer just advances
git merge --no-ff feature/1     # always creates a merge commit (documents every integration)

Git Rebase

Changes the base of a branch to the latest commit, then replays the other commits on top. Gives a clean, linear history, but rewrites commit history (reduces traceability).

git checkout feature/1
git rebase main

Interactive rebase (git rebase -i HEAD~2) lets you replace pick with: reword (edit message), squash (fold in, keep messages), fixup (fold in, discard message), drop (delete), edit (pause to amend).

Golden rule: Never rebase a branch others have already based work on — rewriting shared history forces a painful reconciliation on everyone else. Rebase is for your own unpublished work.

Squash Commits

Not a standalone command — available via interactive rebase or as a merge option. Folds all commits into one, discarding individual commit details. Useful when a feature branch has messy WIP/typo-fix commits.

git rebase -i HEAD~2        # then choose squash/fixup
# or
git merge --squash feature/1
ScenarioTool
Integrating a finished feature into main for a teammerge --no-ff
Keeping your local feature branch current with mainrebase
Cleaning up messy local commits before a PRrebase -i
Delivering a feature as one clean commitmerge --squash
Need a record that two branches were joinedmerge
Want linear, bisectable historyrebase
In an academic context: use git merge --no-ff for labs/projects/research — it lets your supervisor or examiner see the actual process (commit history, branch evolution), not just the final solution. Still practice rebase and squash in a sandbox repo.

14 Commit Messages

git commit -m "Subject line under 72 characters"

Template for a well-structured merge commit message: What was merged and into where? What does the merge accomplish? Were there conflicts, and how were they resolved? Does it meet the assessment/lab requirements?

Why it matters: a well-structured commit message is the difference between submitting an answer and submitting an answer with reasoning — your technical lab notes proving you understood what you did.
git config --global core.editor "code --wait"   # VS Code (recommended for class labs)
git log --oneline                # quick overview
git log --oneline --graph        # quick overview as a graph
git show HEAD                    # full details of the most recent commit

15 Pull Request

Configure branch protection rules on main so a Pull Request (with at least one approval) is mandatory, not optional — otherwise a developer can push straight to main and skip review entirely. Example ruleset: "pr-and-1-approval-required-to-merge", enforcement Active, targeting the Default branch, requiring 1 approval; allowed merge methods left as Merge / Squash / Rebase.

16 Reversing Changes in Git

CommandUse case
git reset <commit> / git reset HEAD~1Reverse local, unpushed changes (unstaged, not lost)
git revert <commit> / git revert HEADSafely undo shared/pushed commits by creating a new "undo" commit — original stays in history

With revert, the target is the commit you want to undo; with reset, the target is the commit you want to land on. Only use reset on commits not yet pushed — once shared, it rewrites history others may have already pulled.

Git Reflog

git reflog is Git's diary of every HEAD movement (resets, rebases, merges, checkouts, commits) — including ones no longer visible in git log.

git reflog --relative-date
git reset HEAD@{51 minutes ago}   # instead of git reset HEAD~1
Limitation: reflog is local-only — not pushed to GitHub, empty on a fresh clone, and entries expire after 90 days by default.

17 Moving Work Around in Git

If you accidentally commit to main (or the wrong branch), use cherry-pick to copy specific commits to the correct branch.

git log --oneline                     # Step 1: get the commit ID
git switch feature/user-profile       # Step 2: switch to the correct branch
git cherry-pick a1b2c3d               # Step 3: apply the commit (new SHA; original untouched)
git reset a1b2c3d                     # Step 4: remove the commit from main
git restore <filename>                # Step 6: discard unstaged changes if needed
git log --oneline                     # Step 5: verify HEAD is in the right place

18 Three-Part Versioning

Semantic Versioning — 2.1.46
MAJOR (2) — significant/incompatible changes MINOR (1) — backward-compatible new features PATCH (46) — backward-compatible bug fixes only

Advantages: standardised communication about the nature of an update, and safe dependency management — package managers can be configured to auto-accept non-breaking Minor/Patch updates only.

19 Git Workflows

The right workflow depends on the application: installable apps needing multiple simultaneous versions (e.g. mobile apps) vs SaaS apps deployed many times a day (e.g. a streaming web app).

WorkflowBest forKey idea
Git Flow (Vincent Driessen, 2010)Installable mobile/desktop apps, large/regulated teamsMultiple long-lived branches: main, release, development, feature, bug/hotfix — supports multiple versions running simultaneously
GitHub FlowMedium-scale SaaS, small agile teamsOne rule: main must always be deployable; medium-lived feature/bug branches
Trunk-Based DevelopmentLarge-scale SaaS (current 2026 industry standard)Direct commits to main + short-lived (~4hr) feature branches, feature flags hide WIP from production

In every workflow: a feature branch addresses an Issue mapped to a functional/non-functional requirement, and a Pull Request should trigger a code review (e.g. from a research supervisor) before merging.

For research supervision: GitHub Flow works well — it gives you 1–4 weeks to work on an issue and gives your supervisor a chance to review multiple commits in one PR, fitting a 2-week sprint/iteration cadence (Scrum/Kanban).

Teams often combine workflows — e.g. trusted internal engineers merge directly into main, while external contributors must go through a PR.

📝 Likely Exam Questions

Q1: Distinguish data mining, data analytics, and business analysis using the student "check-out" example.

Data mining discovers the hidden correlation (library + sports complex absence → risk of "checking out mentally") from raw data without a prior hypothesis. Data analytics takes that pattern and asks a specific question ("how do we intervene?"), producing a recommendation (an Early Alert system) and measuring ROI. Business analysis designs the actual business process that makes the recommendation work — stakeholder interviews, gap analysis, requirement specification, and a new SOP. The three roles are complementary: patterns → insights → solutions.

Q2: Explain the KDD process and why Steps 1–4 matter so much.

KDD has 9 iterative steps: problem definition, data selection, cleansing/pre-processing, transformation, mining task selection, algorithm selection, utilisation, interpretation/evaluation, and consolidation. Steps 1–4 (significant data preparation) must precede mining — without ethically-collected, unbiased, cleaned, and properly transformed data, the resulting model cannot yield information that can be trusted for business decisions, no matter how good the chosen algorithm is.

Q3: Explain the bias-variance trade-off and give one cause of each type of error.

Bias error is the simplifying assumption a model makes (high in linear/parametric models); one cause is biased or skewed training data, e.g. sampling bias from an unrepresentative customer base. Variance error is how much the model's estimate changes across different training batches (high in non-linear/non-parametric models); one cause is model complexity — an overly complex model memorising noise instead of the trend. Reducing bias tends to increase variance and vice versa, so the goal is the "sweet spot" balancing both, typically found via k-fold cross-validation.

Q4: What distinguishes a data product from a raw dataset? List the 6 questions a data product must answer.

A data product is intentionally designed for specific users, tested and validated, delivers ready-to-use insight, and has an accountable owner — unlike raw data, which is passively collected with no defined user or quality guarantee. It must answer: (1) what is the problem (root cause, not symptom), (2) what data sources are needed, (3) what users actually require, (4) what transformations are needed, (5) who the intended users are, and (6) how it ranks in priority against other data products.

Q5: Explain the 7 pillars of DataOps.

(1) ELT — load raw data first, transform after, for speed and auditability (EtLT when PII must be stripped for compliance). (2) CI/CD — frequent integration, build, and test cycles measured in hours/days. (3) Component design and maintainability — small, atomic, well-documented, loosely-coupled code. (4) Environment management — quickly replicate production-like environments via cloud providers. (5) Governance and change control — every change/test/approval documented and retained. (6) Automated data testing — paired with ongoing production monitoring. (7) Collaboration and self-service — a cultural behaviour built on psychological safety and shared accountability, not a tool.

Q6: Compare Git Merge, Git Rebase, and Squash Commits — when should each be used?

Git Merge creates a merge commit preserving full history of both branches — ideal when a record of the joined branches is needed (e.g. --no-ff for academic/audit purposes). Git Rebase replays commits onto a new base for a clean, linear history, but rewrites history — safe only for your own unpublished work. Squash Commits (via rebase or merge) folds all commits into one, useful for delivering a feature as a single clean commit when intermediate WIP commits add noise. In team/academic settings, merge --no-ff is generally preferred so a supervisor or examiner can see the full development process.

Q7: Compare Git Flow, GitHub Flow, and Trunk-Based Development.

Git Flow (Driessen, 2010) uses multiple long-lived branches (main, release, development, feature, bug/hotfix) and suits installable apps needing several versions running simultaneously, at the cost of added complexity and merge-conflict risk. GitHub Flow uses one rule — main must always be deployable — with medium-lived feature/bug branches, suited to medium-scale SaaS and agile teams with CI/CD. Trunk-Based Development uses direct commits to main plus very short-lived (~4 hour) feature branches and feature flags, suiting large-scale SaaS with strong automated testing and a "culture of excellence" — it is the 2026 industry standard for continuous deployment.
