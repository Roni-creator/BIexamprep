1. Distinguish: Data Analyst / Data Miner / Business Analyst / Data Engineer / Data Scientist

Appeared 3×
RoleFocus
Data MinerDiscovers hidden patterns/correlations in large datasets using inductive reasoning, without a prior hypothesis. Output: models and patterns.
Data AnalystStarts from a specific question/hypothesis (e.g. "why did sales drop?"). Extracts insights to support decisions. Uses SQL, Power BI, Excel. Output: reports, visualisations, recommendations.

3. SVM vs Random Forest — Classifying "High Demand" vs "Low Demand"

Appeared 3× — identical wording every time
Support Vector Machine (SVM)Random Forest
Finds the optimal hyperplane (decision boundary) that maximises the margin between "High Demand" and "Low Demand" classes. Can use kernels (e.g. RBF) to handle non-linear boundaries.Builds many decision trees on random subsets of data/features and combines their votes (ensemble/bagging) to classify each product.
Works well with high-dimensional data and clear margins, but the boundary is a mathematical hyperplane — hard to explain intuitively.Each individual tree follows simple if-then splits (e.g. "if past sales > X and season = holiday → High Demand") which non-technical people can follow.

Which is easier to explain to managers? Random Forest — because it's built from decision trees with human-readable if-then rules and feature importance rankings, whereas SVM's hyperplane/kernel math is abstract and harder to translate into plain business language.

4. DAX vs M (Power Query) in Power BI

Appeared 3×
DAX (Data Analysis Expressions): A formula language used to create calculated columns, measures, and calculated tables — it operates after data is loaded into the Power BI data model, performing calculations and aggregations at query/report time.
M (Power Query language): Used in Power Query Editor before data is loaded — for shaping/transforming/cleaning raw data (merging tables, removing columns, changing types, unpivoting, etc.) during the ETL stage.

Key difference: M transforms data on the way in (ETL); DAX calculates and analyses data that's already loaded into the model (reporting/analysis layer).

Example DAX measure:
Total Sales = SUM(Sales[SalesAmount])

This creates a measure that sums the SalesAmount column across whatever filter context is applied (e.g. by region, by month, by product) — it dynamically recalculates depending on how it's sliced in a visual.

5. Decision Tree Partitioning & CART as "Distribution-Free"

Appeared 3×

Two items required to partition the input space

  1. A splitting attribute/feature — which input variable to split on at that node (chosen via a criterion like Gini impurity or information gain).
  2. A splitting value/threshold (split point) — the value of that attribute which divides observations into two (or more) branches, e.g. "Age < 30" vs "Age ≥ 30", or for categorical data, which category goes left vs right.

CART as a "distribution-free model"

It means CART makes no assumptions about the underlying statistical distribution of the input data (unlike parametric models such as linear/logistic regression, which assume things like normality or linearity). CART is a non-parametric algorithm — it partitions the input space recursively based on the data itself, so it can model any shape of relationship without requiring the data to follow a specific distribution (e.g. Gaussian).

6. KDD — 9 Sequential Phases

Appeared 2× — worth 10 marks when asked, highest payoff per minute of memorization
  1. Problem Definition & Goal Setting — understand the problem, end-user requirements, and environment.
  2. Data Selection — discover accessible data, select relevant data, integrate into one dataset; ensure ethical collection and representative sampling.
  3. Data Cleansing & Pre-Processing — remove outliers/noise, impute missing values (e.g. fix invalid postal codes, currency symbols).
  4. Data Transformation — scaling, centering, standardisation, normalisation, encoding (one-hot/label), dimensionality reduction.
  5. Selection of the Data Mining Task — decide to describe (associations/clusters), predict (classification/regression), or optimise/prescribe.
  6. Selection of the Data Mining Algorithm — bench-test several algorithms, shortlist top performers.
  7. Utilisation of the Algorithm — train the model; hyperparameter tuning, ensembling.
  8. Interpretation & Evaluation — validated by domain experts (not the IT practitioner); if invalid, repeat from Step 2.
  9. Consolidation — operationalise the knowledge into an information system/production environment.
Memory trick: "Problem → Select → Clean → Transform → Pick Task → Pick Algorithm → Use it → Judge it → Ship it."

7. Irreducible Error, Bias Error, Variance Error

Appeared 2×
TypeDefinitionBusiness example
Irreducible errorError independent of the model/algorithm; caused by the problem framing itself (e.g. missing variables) — cannot be reduced no matter which algorithm is used.A model predicting loan default can't account for a sudden personal emergency that isn't in any dataset.
Bias errorError from simplifying assumptions the model makes; high in linear/parametric models. Leads to underfitting.A linear regression assumes sales grow at a constant rate, missing seasonal spikes — systematically under/over-predicting.
Variance errorHow much the model's estimate changes when the training data changes; high in complex/non-linear models. Leads to overfitting.A deep decision tree trained on last month's data perfectly fits it, but performs poorly on next month's data because it memorised noise.

Reducing bias tends to increase variance and vice versa — the goal is the balance point (found via cross-validation).

8. Random Forest vs Single Decision Tree (Loan Default)

Appeared 2×

A single decision tree can overfit the training data and is sensitive to small changes (high variance) — a slightly different sample of applicants could produce a very different tree. A Random Forest builds many trees on random subsets of data/features and averages/votes their predictions, which reduces variance and makes predictions more stable and accurate.

Business benefit: More reliable, generalisable default predictions — reducing the risk of the bank approving bad loans or rejecting good customers based on one overfit tree's quirks (i.e. fewer costly misclassifications).

9. Kafka: Topics, Partitions, Brokers, Offsets, Leaders, Followers & ISR

Appeared 2× — updated with exact course terminology from Module 2 notes
  • Topic — an append-only, immutable log (not a queue) holding one category/kind of event. Records are only ever added to the end, never inserted in the middle.
  • Partition — a horizontal fragment of a topic's messages, letting the topic spread across multiple brokers in a cluster. This enables parallel read/write requests, improving throughput and scalability.
  • Offset — a unique sequential ID given to each message within a partition. Consumers track which offset they've read up to, enabling them to resume, skip, or replay messages.
  • Broker — a single Kafka server; many brokers form a Kafka cluster. A single well-resourced broker can store terabytes of messages and handle hundreds of thousands of reads/writes per second.
  • Leader — every partition has exactly one broker acting as leader, which handles all reads and writes for that partition.
  • Follower — replicates the leader's log to maintain a consistent copy, but does not serve read/write requests directly. If the leader fails, a follower is promoted to leader.
  • ISR (In-Sync Replicas) — only followers that are sufficiently up-to-date with the leader are eligible for promotion. This guarantees consistency and prevents a "split-brain" scenario (two brokers both thinking they're the leader).
Broker/partition distribution rule: N partitions with N brokers → 1 partition per broker. More brokers than partitions → extra brokers get none. Fewer brokers than partitions → some brokers hold multiple partitions (not recommended — causes uneven load).

Why this gives scalability + fault tolerance: Partitions spread across brokers let Kafka process reads/writes in parallel (scalability); leader/follower replication with ISR means a broker failure doesn't lose data or availability (fault tolerance).

10. Kafka Connect: Connectors, Transforms, Converters

Appeared 2× (converters asked with 3 format examples in one paper) — updated with course-exact memory aid

Kafka Connect is a framework for scalable, fault-tolerant streaming integration between Kafka and external systems (databases, cloud services, search indexes, key-value stores). External systems act as sources (upstream — data flows into Kafka) or sinks (downstream — data flows out of Kafka).

  • Connector — the plugin (packaged as a JAR) that links Kafka to an external system; built by vendors (Confluent) or open-source (Debezium). Connectors move data.
  • Transform (SMT — Single Message Transform) — optional, lightweight per-record changes as data passes through (renaming a field, deleting PII, replacing N/A with NULL). Transforms modify data. This lightweight "t" is the lowercase t in EtLT.
  • Converter — handles serialisation/deserialisation of data, independent of which connector is used. Converters format data. Common formats: JSONConverter (human-readable, larger payload), AvroConverter (compact binary, works with Schema Registry), ProtobufConverter (compact, strongly typed, by Google).
Memory aid (suitcase analogy): Serialisation is like packing clothes into a suitcase before a flight — you can't carry clothes loose onto a plane, you pack them into a structured, portable format. On arrival, you unpack (deserialise).
Trivial (SMT) vs non-trivial transforms: SMTs handle each record independently with minimal memory (renaming, type conversion, PII removal) — no joins/aggregations/windowing. Non-trivial work (aggregations, joins, pattern detection, ML training) is stateful and compute-intensive, requiring a dedicated stream-processing layer like Apache Flink, Kafka Streams, ksqlDB, or Spark Structured Streaming — not something Kafka Connect itself does.

11. Gini Impurity Calculation

Appeared 2× — practice the formula itself

Formula: Gini = 1 − Σ(pᵢ)², where pᵢ is the proportion of each class within a group.

Worked example (using the "Made Repeat Purchase" outcome, 10 rows, 5 Yes / 5 No):

For a feature like "Subscribed to Newsletter" — split the data into Yes-subscribers and No-subscribers, then compute the Gini impurity of the "Made Repeat Purchase" outcome within each branch, and take the weighted average across branches.

Steps to answer this type of question:
  1. Split the dataset by the feature's values (e.g. Yes/No).
  2. Within each split, count how many "Yes"/"No" outcomes there are for the target (Made Repeat Purchase).
  3. Compute Gini for each branch: 1 − (p_yes² + p_no²)
  4. Weight each branch's Gini by (branch size ÷ total size) and sum → that's the feature's overall Gini impurity.
  5. Repeat for every feature; the feature with the lowest weighted Gini impurity is the best split (purest separation).
Sanity check: Gini = 0 means a branch is perfectly pure (all one class); Gini = 0.5 means a 50/50 split (maximum impurity for 2 classes).

12. Diagnostic EDA — Residuals vs Fitted / Component+Residual Plots

Appeared 2× (2 different plot types, same logic) — updated with full Diagnostic EDA table from Module 2

These plots belong to Diagnostic EDA — done after a statistical test, to confirm its assumptions hold (otherwise the p-value can't be trusted). Full assumption table:

AssumptionTest/PlotPass condition
Linearity (X→Y relationship)Residuals vs Fitted plotNo pattern; residuals scattered randomly around the 0.0 line
Independence of errorsDurbin-Watson test (H₀: no autocorrelation)DW statistic close to 2; p > 0.05 → fail to reject H₀ → pass
Normality of residualsQ-Q plot (not relevant for logistic regression)Points fall along the straight diagonal line
Homoscedasticity (equal variance)Scale-Location plot + Breusch-Pagan test (H₀: homoscedastic)Points randomly scattered, roughly horizontal fitted line; p ≥ 0.05 → pass

For a Residuals vs Fitted (or Component+Residual) plot specifically: Describe the pattern you see — a random, flat scatter around zero (no curve, no funnel/fan widening) signals the assumption passed; a visible curve or systematically widening/narrowing spread signals non-linearity or heteroscedasticity, meaning it has not passed. Judge the actual plot given in the question against this — don't just assume it passes.

13. EDA Data Types: Nominal, Ordinal, Interval, Ratio

Appeared 2× — updated with course's exact Dimensions vs Measures framing

Your course splits data into two groups first: Dimensions (categorical/qualitative data used to organise into groups — e.g. species, county, gender) and Measures (quantitative/numeric data you can do math on — e.g. revenue, quantity sold). This distinction determines which statistical test is appropriate — you can average "age" but not "religion".

TypeGroupDefinitionExample
NominalDimensionOrdering of values has no intrinsic meaningCounties in Kenya, gender, eye colour
OrdinalDimensionOrdering has intrinsic meaning — every value has its placeEducation level (1st/2nd/3rd year), satisfaction ratings, credit ratings
IntervalMeasureNumeric, equal intervals, but can go below zero (zero is not "absence of")Temperature in °C/°F
RatioMeasureNumeric, equal intervals, cannot go below zero — zero means true absence of the quantityAge, height, sales, number of customers

Measures are also either discrete (countable whole numbers) or continuous (infinitely divisible). Time series and spatial data are additional dimension types: time series pairs each value with a date/time (e.g. sales per quarter); spatial data uses coordinates/geometries (points, lines, polygons).

15. Preventing Overfitting in Non-Parametric Algorithms

Appeared 2×

Why it's a disadvantage: Non-parametric models (e.g. deep decision trees, kNN with small k) are highly flexible and can fit the training data so closely that they capture noise and outliers rather than the true underlying trend — this hurts generalisation to new/unseen data (high variance).

Two prevention techniques:

  • Cross-validation (e.g. k-fold) with a held-back validation/test set — detects overfitting by checking if performance holds on unseen folds.
  • Regularisation / pruning — penalising model complexity (e.g. pruning a decision tree, limiting max depth, L1/L2 regularisation) to force the model to focus on broader trends rather than memorising every data point.

16. One-Off Topics (each appeared once — know the core idea, don't over-invest time)

Appeared 1× each

Change Data Capture (CDC) + Debezium

Updated with precise Module 2 detail

CDC lets you extract every INSERT, UPDATE, and DELETE from a database into a real-time stream of events, instead of waiting to batch-load data hours later — supporting "as close to real-time as possible" analytics for a 24-7 economy.

Debezium is a set of distributed, Kafka Connect–compatible source connectors. It reads the database's own transaction log (e.g. PostgreSQL's WAL, MySQL's binlog) directly — not the application — detects row-level changes, and emits each one as a Kafka event containing the "before" and "after" state, in the exact order the changes occurred. Downstream Kafka consumers then read these events and react in real-time.

ClickHouse — Column-Oriented Data Warehouse Architecture

Updated with precise Module 2 detail

ClickHouse is an open-source, distributed, column-oriented OLAP database (built by Yandex, 2009; used by Uber, Spotify, Cloudflare, GitLab and others), claimed to be up to 100× faster than MySQL for analytical workloads.

Row-oriented vs column-oriented: row-oriented databases (PostgreSQL, MySQL — good for OLTP/CRUD) store all columns of a row together, so a query like SELECT AVG(age) FROM emp still reads every column of every row. Column-oriented ClickHouse stores each column separately, so that same query reads only the age column — minimising I/O. Same-type values stored together also compress far better.

Architecture: a ClickHouse cluster is made of shards (each a group of replicas), using asynchronous multi-master replication — data can be written to any available replica and is then propagated to the rest. ZooKeeper coordinates cluster processes but is not involved in actual query execution. This lets ClickHouse generate reports from petabytes of data with sub-second latency.

Multicollinearity & VIF

Multicollinearity = when two or more predictor variables in a regression are highly correlated with each other. VIF (Variance Inflation Factor) values above ~10 (some use 5) indicate serious multicollinearity — e.g. YouTube (82.14), TikTok (47.31), Facebook (103.47) are all severely collinear. Problem: it becomes impossible to isolate each predictor's individual effect on the outcome — coefficients become unstable and hard to interpret. Fix: remove/combine correlated predictors, or use regularisation (e.g. Ridge regression), or use Principal Component Analysis (PCA).

Kaplan & Norton's Balanced Scorecard

Four perspectives, top-down from Mission/Vision → Strategic Objectives → KPIs:

  • Financial ("How do we look to shareholders?") — e.g. revenue growth %
  • Customer ("How do customers see us?") — e.g. Net Promoter Score
  • Internal Business Processes ("What must we excel at?") — e.g. order fulfilment time
  • Innovation & Learning ("Can we improve and create value?") — e.g. employee training hours

Leading vs lagging indicators: A leading indicator predicts future performance (e.g. employee satisfaction → predicts future customer satisfaction); a lagging indicator records past performance only (e.g. last quarter's sales increase). A good dashboard needs both.

Five Dashboard Design Principles

  1. Compactness/Modularity — fits in the viewer's mind, broken into digestible pieces — avoids cognitive overload.
  2. Gradual Reveal — key metrics first, then context, then detail — prevents overwhelming the audience.
  3. Guided Attention — colour/position/alerts draw the eye to what matters most — ensures critical info isn't missed.
  4. Minimise clutter (data-to-ink ratio) — remove decorative elements, avoid unnecessary 3D/gridlines — speeds up comprehension.
  5. Lead to Action — the dashboard should make clear what to do next — turns information into decisions.

Logistic Regression — Odds Ratio Interpretation

An odds ratio (OR) > 1 means the predictor increases the odds of the outcome; OR < 1 means it decreases the odds. E.g. Support Calls OR = 2.01 → each additional support call more than doubles the odds of renewal (holding other variables constant). Monthly Fee coefficient is negative because higher fees make renewal less likely (OR = 0.96, i.e. odds decrease slightly per unit increase in fee). % change in odds = (OR − 1) × 100 — e.g. Customer Age OR = 1.03 → a 3% increase in odds of renewal per year of age. AUC of 0.72 indicates modest-to-acceptable discriminative ability (better than random guessing at 0.5, but not excellent — usually 0.7–0.8 is considered acceptable). One limitation of logistic regression: it assumes a linear relationship between predictors and the log-odds of the outcome, and struggles to capture complex non-linear relationships without manual feature engineering.

Power BI: Table Relationships & Creating a Bar Chart

Relationships connect tables (e.g. a Sales table to a Products table) via a common key/column, enabling data from multiple tables to be combined in one visual without duplicating data — created in the Model view by dragging one table's key field onto the matching field in another table.

Bar chart steps: (1) Load and clean data via Power Query, (2) go to Report view, (3) select the Bar Chart visual from the Visualizations pane, (4) drag a categorical field (e.g. Region) to the Axis and a numeric field (e.g. Sales) to Values, (5) Power BI aggregates the numeric field (usually Sum) per category, (6) interpret by comparing bar lengths across categories to spot the highest/lowest performers.

Quick Measures vs DAX

Quick Measures are pre-built calculation templates in Power BI's UI (e.g. running total, % of total) that generate DAX automatically without you writing it. Use them for common calculations to save time and reduce errors. Limitation: less flexible/customisable than hand-written DAX, and can produce more complex/less optimised code than an experienced author would write by hand.

Four Stages of the Data Pipeline: Ingest, Store, Process, Consume

  • Ingest — collecting raw data from sources (APIs, sensors, transactional systems) into the pipeline.
  • Store — persisting the data in a data warehouse, lake, or mart for durability and later access.
  • Process — cleaning, transforming, and/or modelling the data (ETL/ELT, feature engineering).
  • Consume — the processed data is used via dashboards, reports, APIs, or ML models to drive decisions.
